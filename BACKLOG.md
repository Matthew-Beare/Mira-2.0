# MIRA 2.0 BACKLOG

This backlog is **not FIFO**. Arrival order never determines implementation order. Priority is recomputed from blockers, dependencies, milestone value, architectural leverage, user-visible value, and verification needs.

## Priority classes

1. **BLOCKER** — data integrity, privacy, security, or active acceptance blocker.
2. **PREREQUISITE** — hard dependency for higher-value work.
3. **VERTICAL** — user-visible end-to-end slice for active milestone.
4. **HARDENING** — reliability, testing, migration, observability, recovery.
5. **ENHANCEMENT** — useful but not required for active proof.
6. **LATER** — valid direction intentionally outside current milestone.

## Canonical authority dependency findings

- G1 normalizes to `AUTH-001` + `STORE-001`; Google Sheets/Drive are adapter choices/default deployment evidence, not semantic domain IDs.
- `AUTH-001` owns exact one-authority-per-data-class routing and Authority Registry metadata. Physical resource/failure-domain separation does not create multiple writable truths.
- `STORE-001` keeps structured-state and retained-evidence adapter roles distinct and requires exact read/write/readback behavior appropriate to the selected role. Provider brand is never capability proof.
- Git remains source/policy/schema/test/lineage authority through `DEV-001`/`SOURCE-001`; it is not the routine mutable-state or evidence-body database.
- Legacy G1's `source-mutation` dependency is too broad for runtime state. Source write/readback gates durable behavior/policy/schema changes, not ordinary canonical-state transactions.
- Legacy G1's `integration-registry` dependency is also too broad as a universal state blocker. Adapter health/configuration must be observable, but unrelated integration-catalog failure cannot manufacture canonical-state failure.
- Capability/dependency routing is test-verified for structured/evidence read-write-readback and module-scoped block/degrade semantics; the persistent generic Authority Registry and generic adapter execution are not implemented in audited legacy main.
- PR #31 remains partial candidate evidence: Google-default provider policy, a separate storage-portability experiment, and direct SQLite service commands/readback exist, but no generic Authority Registry/cutover engine or coherent live multi-topology proof exists.
- Provider/backend migration requires `AUTHORITY-MIGRATION-001`: source checkpoint/backup, canonical export, target dry run/import, UUID/hash/relationship parity, bounded target write/readback, recovery proof, explicit cutover and rollback retention. A migration target is never a second writable master.
- `DATA-SANDBOX` now explicitly depends on `AUTHORITY-REGISTRY-001`, `STORE-ADAPTER-001`, and `GOOGLE-BOOTSTRAP-001`; this makes the synthetic MIRA 2.0 provider namespace depend on the authority contract rather than the previous vague “canonical state contract.”

## G7/API dependency findings

- G7 normalizes to `API-001`, the versioned authenticated client/service boundary in front of `AUTH-001`/`STORE-001`; it is not a datastore and using it never makes a client authoritative.
- Safe mutation requires server-side actor/client authentication, exact resource/action authorization, dependency/capability and compatibility preflight, stable canonical IDs, mandatory idempotency, conflict/version handling, canonical write, exact readback and audit.
- `PROFILE-013` remains permission truth for cross-person/shared access. Relationship labels, provider connection or possession of a device token cannot grant scope by themselves.
- API/schema incompatibility fails closed for mutation. Unknown mutation classes do not fall back to permissive behavior; the server owns conflict semantics where races matter.
- Remote transport requires TLS. Public exposure additionally requires scoped short-lived credentials, rate limiting and auditable server authorization. Personal deployments may prefer a private overlay but still use the same authorization semantics.
- `API-CORE-001` is a BLOCKER before stock ChatGPT or Android are allowed to perform canonical remote mutation. `CORE-ROUNDTRIP` now depends on it so both surfaces prove one shared path.
- PR #31 remains salvage/reference only: useful FastAPI, compatibility, device enrollment, audit/readback and idempotency candidates exist, but scoped authorization, mandatory mutation gates, generic conflicts and `AUTH-001`/`STORE-001` adapter routing are incomplete.
