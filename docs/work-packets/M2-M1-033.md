## Implemented behavior

- `StudioSourceTarget` binds provider ID, service ID and logical target reference without credential or endpoint material.
- `StudioSourceState` and `StudioSourceMutationResult` carry exact revision/source/state/evidence digests through an injected adapter contract.
- `execute_studio_activation` requires an existing `StudioActivationPlan`; this module cannot create approval authority.
- READ, WRITE and REMOTE_READBACK capability decisions are independently required and must match the target provider/service identity before source access proceeds.
- Missing, denied or ambiguous required gate evidence blocks before source access or mutation.
- Activation preflight requires the current revision to equal the plan base revision and current state digest to equal the recorded rollback-state anchor before write.
- The injected adapter receives exact change ID, expected current revision, reviewed proposal revision and reviewed source digest; the core emits no provider-specific command, shell or credential material.
- Adapter exceptions after mutation attempt are recorded as `recovery_required` with unknown outcome rather than being misreported as a clean failure.
- Mutation disposition explicitly distinguishes `not_attempted`, `performed` and `unknown`.
- A mutation result that reports an unchanged revision or wrong approved source digest cannot become activation success.
- Activation success requires exact remote readback matching the adapter-returned applied revision/source/state.
- Applied target revision is intentionally allowed to differ from the reviewed candidate SHA because a merge/cherry-pick adapter may create a new target commit; the exact reviewed proposal SHA and approved source digest remain adapter inputs, and the approved source digest remains part of success verification.
- A prior successful exact activation receipt enables deterministic zero-write replay only when current remote revision/source/state match that receipt exactly.
- Activation never automatically rolls itself back.
- `execute_studio_rollback` requires the original plan, a successful matching activation receipt, verified capability and exact current applied state.
- Rollback receives only the recorded prior revision/state anchor and expected current applied revision.
- Stale rollback state blocks with zero mutation; rollback write/readback uncertainty becomes recovery-required rather than fabricated success.
- Activation and rollback receipts are deterministic and secret-free.

## Review note — proposal SHA versus applied revision

A mid-review concern considered requiring `applied_revision_sha == plan.proposed_sha`. That restriction was rejected because a correct merge/cherry-pick source adapter may create a different target revision while applying the exact reviewed source. The contract therefore preserves the distinction deliberately: `plan.proposed_sha` and approved `source_sha256` are exact adapter inputs; success requires the mutation source digest to equal the approved digest and remote readback to match the adapter-returned target revision/source/state. Provider-specific ancestry/history verification remains an adapter/source-lane responsibility rather than being fabricated by provider-neutral core code.
