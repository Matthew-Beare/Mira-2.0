## Objective

Implement the capability-based model profile and benchmark evidence seam required by the optional compute fabric. Public product logic must be able to evaluate whether a model profile satisfies explicit task requirements without hard-coding a model family, machine, accelerator, path, provider endpoint, benchmark score or quality threshold.

This packet is profile/evidence evaluation only. It does not install a model, load weights, execute inference, benchmark a live worker, persist private deployment binding, alter worker routing or claim a live model capability.

## Model profile contract

A profile contains only sanitizable logical facts:

- `profile_id`;
- `runtime_id`;
- `artifact_id` and SHA-256 digest;
- sorted unique generic capability IDs;
- explicit context-window token capacity;
- explicit maximum output-token capacity.

No model path, hostname, IP/MAC, accelerator identity, serial number, credential, raw command or provider-private resource is part of the profile schema.

Model family names are not required. A deployment may choose to use a family name as a logical profile ID, but no MIRA feature may depend on that name.

## Benchmark evidence contract

Each benchmark observation contains:

- profile ID;
- benchmark ID and benchmark version;
- capability ID being evidenced;
- metric ID;
- finite numeric metric value and explicit unit;
- UTC observation time;
- positive sample count;
- explicit evidence kind: `measured`, `imported` or `synthetic`;
- provenance SHA-256 digest.

The observation does not establish benchmark meaning by itself. Selection authority comes only from explicit benchmark requirements supplied by policy/task configuration.

## Benchmark requirement contract

Each requirement specifies:

- benchmark ID/version;
- capability ID;
- metric ID;
- comparator `at_least` or `at_most`;
- explicit numeric threshold;
- exact unit;
- maximum evidence age in seconds;
- non-empty allowed evidence-kind set.

Public code provides no benchmark threshold defaults. Synthetic test values are test fixtures only and cannot become production thresholds.

## Selection request contract

A selection request specifies:

- sorted unique required generic capabilities;
- minimum context-window tokens;
- minimum maximum-output tokens;
- zero or more benchmark requirements;
- optional ordered preferred profile IDs.

Preference ordering is explicit policy. If no eligible preferred profile exists, the evaluator uses stable profile-ID ordering only as a deterministic tie-break. It must not invent a quality ranking from profile names or unrequested metrics.

## Evaluation semantics

For each profile:

1. Required capabilities must be a subset of declared profile capabilities.
2. Context and output capacities must meet explicit minima.
3. Every benchmark requirement must have exactly one matching observation for that profile and exact benchmark/version/capability/metric key.
4. Matching observation must use the required unit.
5. Matching observation must use an allowed evidence kind.
6. Observation must not be from the future and must be fresh enough at explicit evaluation time.
7. Metric value must satisfy the explicit comparator/threshold.
8. Extra observations are ignored for eligibility and do not gain authority.

Duplicate observations for the same profile+benchmark+version+capability+metric key fail closed because selecting which duplicate is authoritative would otherwise be arbitrary.

## Result contract

Evaluation returns:

- deterministic profile evaluations sorted by profile ID;
- each profile's eligible flag and sorted unique blocker reason codes;
- selected profile ID or `None` when none are eligible;
- deterministic selection reason code describing preferred-policy selection, stable tie-break selection or no eligible profile.

The result is evidence for later runtime routing. It does not choose a worker, mutate registry state, load a model or execute a task.

## Acceptance evidence target

1. Profile validation rejects malformed IDs/digests, duplicate/unsorted capabilities, and invalid context/output capacities.
2. Benchmark observation validation rejects malformed IDs, non-finite values, invalid evidence kind/sample count/time/digest.
3. Requirement validation rejects malformed comparator, non-finite threshold, invalid unit/freshness or duplicate/unsorted allowed evidence kinds.
4. Capability/context/output gates fail closed.
5. Exact `at_least` and `at_most` threshold boundaries pass.
6. Below/above threshold failures are deterministic.
7. Missing, stale, unit-mismatched and disallowed-kind benchmark evidence blocks eligibility.
8. Future benchmark evidence fails closed.
9. Duplicate matching observation keys fail closed.
10. Extra unrelated observations do not influence eligibility.
11. Explicit profile preference order wins among eligible candidates; ineligible preferred candidates are skipped.
12. Without a usable preference, stable profile-ID ordering provides deterministic tie-breaking only.
13. Profile and observation input order cannot change the result.
14. Result/profile schemas contain no private deployment/execution fields.
15. Production ownership is explicit with direct tests.
16. Exact-head CI passes before merge and post-merge main CI passes before integration verification.
17. No live model/runtime/benchmark claim is made.
