## Objective

Implement a provider-neutral deterministic lifecycle planner that can tell a later trusted executor what must or may happen to one compute worker without performing the action itself.

Inputs are existing validated worker/job/safety views plus explicit lifecycle intent, power observation and locks. Output is immutable, secret-free action material suitable for later adapter execution/readback.

## Lifecycle intent contract

Supported intents are intentionally narrow:

- `steady` — reconcile whether new MIRA work may be admitted and whether current work should drain because of locks/state/safety;
- `wake` — request eligibility to wake an explicitly managed worker that is observed off;
- `drain` — stop admitting new work and gracefully finish/checkpoint assigned active jobs;
- `shutdown` — gracefully drain first, then request safe shutdown only when assigned active jobs are clear;
- `safety_reconcile` — apply an explicit `ComputeSafetyDecision` including immediate stop/fault requirements when configured safety demands them.

## Lock contract

Lifecycle locks are explicit input, not inferred from machine names or presence:

- `do_not_wake` blocks wake action.
- `do_not_shutdown` blocks shutdown action. If deterministic safety requires shutdown, the result retains the blocked safety requirement and marks operator/human resolution required.
- `maintenance_lock` blocks new work and wake, and requests drain of current MIRA work.
- `interactive_lock` blocks new MIRA work and requests graceful drain/checkpoint so the user can reclaim the worker. It does not override critical/sensor-fault stop/fault requirements.

The existing durable `WorkerRegistryView.interactive_lock` is also authoritative. Effective interactive lock is true when either the worker view or explicit lifecycle-lock input says it is true.

## Power observation contract

Public planner code recognizes only generic power states:

- `on`
- `off`
- `starting`
- `stopping`
- `unknown`

The state is external evidence. This packet does not discover it.

## Worker/job composition

Only nonterminal jobs whose `lease_worker_id` matches the target worker are considered assigned active work.

For ordinary drain/interactive/maintenance/graceful-shutdown behavior:

- active work gets a `finish_or_checkpoint` requirement;
- no destructive stop is inferred merely from a drain request.

For safety decisions with `stop_workloads=True`:

- assigned active work gets `stop_required`;
- planner output also requires node fault state when the safety decision requires it.

The planner never fabricates checkpoint IDs, cancellation acknowledgements or result provenance. Existing `ComputeJobControlPlane` owns those durable mutations.

## Wake semantics

A wake request is eligible only when:

- observed power state is `off`;
- worker is not faulted;
- no do-not-wake, maintenance or effective interactive lock is active;
- an optional supplied safety decision does not itself block admission/drain/fault the node.

If blocked, the result contains deterministic reason codes and no wake request.

## Shutdown semantics

Ordinary shutdown is graceful:

- block new work;
- request drain;
- require assigned jobs to finish/checkpoint;
- request safe shutdown only after no assigned active jobs remain;
- respect `do_not_shutdown` absolutely.

Safety-driven shutdown is stronger:

- stop/fault requirements come from `ComputeSafetyDecision`;
- when `require_safe_shutdown=True`, request shutdown if not locked;
- when `do_not_shutdown=True`, retain `safe_shutdown_required_but_locked` and require operator/human resolution rather than erasing the safety requirement.
