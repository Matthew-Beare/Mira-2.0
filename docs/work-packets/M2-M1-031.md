## Objective

Implement a provider-neutral deterministic evidence/planning seam for competitive Studio development. Multiple independent implementers may produce candidates for the same bounded work packet, but MIRA must compare them using explicit acceptance/test/critique evidence and preserve exact Git provenance. A candidate does not become integration authority merely because it exists, merges cleanly or comes from a favored model/provider.

This packet does not create Git branches, invoke models/providers, execute tests, schedule private runners, merge code or activate a Studio feature. It validates supplied evidence and produces integration-readiness/planning material only.

## Work specification contract

A work specification contains:

- packet/work ID;
- exact base SHA;
- sorted unique feature IDs;
- sorted unique acceptance-criterion IDs;
- sorted unique required verification-suite IDs;
- whether independent critique is required.

It contains no model name, provider credential, private runner identity, host binding or subjective numeric quality score.

## Candidate contract

Each candidate contains:

- logical candidate ID;
- logical producer ID;
- unique Git branch name;
- exact base SHA;
- exact head SHA distinct from base;
- sorted unique acceptance-criterion IDs claimed implemented;
- source/artifact SHA-256 digest.

All candidates in one evaluation must target the same work specification/base. Branches and candidate IDs must be unique. The module does not create or fetch those branches.

## Verification evidence contract

Each verification item contains:

- candidate ID;
- exact candidate head SHA;
- verification-suite ID;
- outcome `passed` or `failed`;
- evidence SHA-256 digest.

Every required suite must have exactly one matching evidence item for the exact current candidate head. Evidence from a stale/different SHA has no authority. Duplicate suite evidence fails closed rather than choosing one arbitrarily.

## Critique evidence contract

Each critique contains:

- target candidate ID and exact target head SHA;
- logical critic ID;
- finding ID;
- severity `blocking` or `non_blocking`;
- resolution `open`, `resolved` or `accepted_risk`;
- evidence SHA-256 digest.

When independent critique is required, an integration-ready candidate needs at least one critique whose critic ID differs from that candidate's producer ID. Any open blocking critique makes the candidate not integration-ready. Resolved/accepted-risk findings retain provenance without blocking.

## Reviewer selection contract

Competitive evaluation determines integration readiness; it does not infer a subjective winner.

- Without explicit reviewer selection, multiple eligible candidates remain a deterministic sorted eligible set and no integration plan exists.
- A reviewer selection names reviewer ID, selected candidate ID and exact selected head SHA.
- The selected candidate must be integration-ready and the selected SHA must exactly match current candidate evidence.
- Reviewer selection produces a bounded integration plan naming the selected branch/head and preserved provenance. It performs no merge.

## Acceptance evidence target

1. Work/candidate/evidence validation rejects malformed IDs, SHA/digests and unsorted/duplicate sets.
2. Candidate IDs and branches are unique; all candidates target the exact packet base and heads differ from base.
3. Missing acceptance-criterion coverage blocks a candidate.
4. Every required verification suite must pass on the exact candidate head.
5. Missing, failed, stale-head or duplicate verification evidence blocks/fails closed.
6. Independent critique policy cannot be satisfied by the candidate producer critiquing itself.
7. Open blocking critique blocks; resolved/accepted-risk critique remains provenance without blocking.
8. Critique evidence bound to a stale/different head fails closed for that candidate.
9. Candidate/evidence input order cannot change deterministic evaluations or eligible ordering.
10. Multiple eligible candidates are not auto-ranked by model/provider identity or inferred quality.
11. Explicit reviewer selection must target an integration-ready exact candidate head.
12. Integration plan is immutable evidence/planning only and cannot execute Git/provider/model/private-runner actions.
13. Schemas/results contain no credentials, private hosts, model paths or subjective hidden scores.
14. Production ownership is explicit with direct tests.
15. Exact-head CI passes before merge and post-merge main CI passes before integration verification.
16. No live competitive model execution, private runner, Git branch creation or merge execution is claimed.
