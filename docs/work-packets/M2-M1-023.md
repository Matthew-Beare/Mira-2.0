## Objective

## Acceptance criteria

1. Worker records use a dedicated STORE-001 resource type and schema version without changing canonical service-state semantics.
2. Initial registration requires verified identity evidence whose principal is durably bound to the worker.
3. Durable worker state stores only secret-free logical material: worker/principal/lane/runtime/service IDs, runtime kind, capabilities, policy values, availability, health, lock, priority/load/cost ranks and heartbeat timestamp.
4. Credentials, tokens, hostnames, IP/MAC addresses, device serials, model paths and raw execution endpoints are absent from the durable schema.
5. Registration is replay-safe with explicit expected revision zero; identity collision or conflicting replay fails closed through STORE-001 semantics.
6. Heartbeat/update requires the same principal identity, verified evidence not newer than the heartbeat, optimistic revision and an idempotency key.
7. A worker cannot silently change principal identity after registration.
8. Query/list ordering is deterministic by worker ID.
9. Registry readback validates persisted shape before exposing a view.
10. Runtime-router projection consumes a validated registry view plus externally supplied `ProviderCapabilitySnapshot`; the registry does not invent provider authorization/read/write/readback evidence.
11. Heartbeat freshness remains evaluated at projection time; stale state is not silently mutated merely because time passed.
12. Tests cover registration, replay, principal mismatch, revision conflict, heartbeat mutation, invalid chronology, deterministic query, secret-free persistence, stale projection and provider-capability separation.
13. Exact-head CI must pass before merge. No live worker, network transport, queue, WOL/shutdown, model load or private deployment claim is made.

## Implemented behavior

- Added dedicated `compute_worker` STORE-001 resource/schema to `mira/service_state.py`.
- Added `WorkerRegistryIdentityEvidence`, `WorkerRegistryView`, and `WorkerRegistryService`.
- Registration persists only verified secret-free worker state and uses expected revision zero for collision-safe creation.
- Heartbeat/update preserves immutable principal/lane/runtime/service/policy identity while allowing bounded mutable execution evidence to advance.
- Identity verification and heartbeat timestamps cannot move backwards; future and identity-after-heartbeat chronology fail closed.
- Exact worker readback validates an exact supported persisted field set before exposing a registry view.
- Deterministic worker listing sorts by worker ID.
- Added `worker_registry_view_to_advertisement` in `mira/runtime_router.py` so validated durable state can enter the existing M2-M1-022 worker projection path without circular imports.
- External `ProviderCapabilitySnapshot` remains mandatory at projection time, preserving SOURCE-001/PROVIDER-001 authority separation.
- Stale heartbeat evaluation remains a read-time projection concern: stale records project to OFFLINE/UNKNOWN and cannot be selected.

## Defect found and corrected during implementation

Review found that the first heartbeat implementation re-read the now-incremented worker revision before an exact retry. Because STORE-001 includes `expected_revision` in the idempotency fingerprint, that could turn a legitimate exact retry into an idempotency conflict.

The correction reads the exact persisted record, rebuilds the requested heartbeat payload, and treats an exact already-persisted payload as deterministic replay/no-op readback without incrementing revision. Changed material still reaches STORE-001 and a reused idempotency key fails closed. The isolated correction commit changed only the heartbeat method, and its diff was audited before proceeding.
