## Acceptance criteria

1. A staged change declares logical change ID, packet/work IDs, change kind, exact base/proposed Git SHAs, source digest, feature IDs, declared contract IDs and required test-suite IDs.
2. Proposed SHA must differ from base SHA; all logical sets are sorted/unique and malformed material fails closed.
3. Preview evidence is bound to the exact change/proposed SHA/source digest and records exactly which declared contracts are covered.
4. Missing declared preview coverage blocks review readiness; unknown preview contract IDs do not gain authority.
5. Each required test suite requires exactly one passing evidence record bound to the exact change/proposed SHA. Missing, failed, stale-head or duplicate required evidence blocks.
6. Extra unrequired test evidence cannot make a proposal ready and is excluded from activation authority.
7. Rollback material is bound to the exact change/base SHA and retains an explicit prior logical revision plus pre-change state digest.
8. Missing/mismatched rollback material blocks review readiness.
9. A review-ready proposal still produces no activation plan without explicit approval.
10. Explicit approval must bind approver, change ID, exact proposed SHA, exact preview digest and approval evidence digest. It cannot override preview/test/rollback blockers.
11. An approved activation plan preserves exact base/proposed/source/preview/test/rollback/approval provenance and contains no execution side effect.
12. Evidence input ordering does not change the deterministic decision.
13. Public staged-lifecycle contracts expose no credentials, provider endpoints, host/network identities, model paths, shell commands, runner labels or automatic-execution fields.
14. Existing M2-M1-031 competition behavior and tests remain green.
15. Required repository CI passes on the exact packet head before merge, followed by post-merge exact-SHA CI before integration verification.
