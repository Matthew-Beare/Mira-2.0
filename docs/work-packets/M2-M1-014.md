## Objective

Non-destructively reconcile newly supplied private financial evidence into the existing MIRROR financial reality while preserving established history and forecast assumptions, then represent private allocation, planning, recurring-obligation, and spending-classification semantics without creating a second finance authority or double counting cash.

## Single-MIRROR invariant

MIRA has one logical MIRROR reality database. Financial Escape tabs are class tables, controls, source-evidence views, or derived projections inside that model; they are not independent databases or co-equal authorities.

- `Entity Registry` owns stable entity identity.
- `FinOps Relations` owns explicit provenance/evidence relationships.
- `FinOps Ledger` owns the integrated economic-event projection used by spending analytics.
- `Subscriptions` owns the recurring-obligation projection backed by provider/user evidence.
- `Planning Items` and allocation/control views represent planned state without mutating provider balances.
- Source-evidence and analytics tabs are human-readable views over those facts. Materially different source assumptions may remain visible without becoming a second authority or overwriting the primary forecast.
- Human review tabs may collect explicit user inputs keyed by stable IDs, but resolved/effective state belongs to the canonical MIRROR class table and is read back into the view rather than independently recomputed.

## Scope / invariants

1. Newly supplied private sources are read-only evidence and comparison/scenario inputs, not permission to overwrite the established Financial Escape budget basis.
2. Materially different source assumptions remain visible as source-evidence state within the same MIRROR model; they do not become a separate database and do not destructively rewrite historical or forecast state.
3. Linked provider balances remain provider observations; allocation semantics must not alter provider balances.
4. Protected reserves and ordinary allocations remain distinct when their funding semantics differ, preventing double subtraction.
5. Existing transaction, snapshot, normalized-spend, debt, productive-work, and forecast history remains intact.
6. User-confirmed recurring allocations use forward starting-state semantics and do not retroactively fabricate prior-period accruals.
7. A combined recurring allocation must not be counted again merely because it is represented by multiple private sub-balances.
8. No purchase/debit automation against allocation balances is activated in this packet; future reconciliation remains separate work.
9. Spending classification keeps three independent axes: purpose category, necessity, and allowance. Vocabulary may expand without rewriting prior selections.
10. All private provider/document identifiers, personal descriptors, and private values remain outside public Git.

## Acceptance criteria

- Read private financial evidence without mutating the source.
- Preserve the current Financial Escape core budget/forecast basis when replacement would materially change established outputs.
- Register source evidence and relationships in the same private entity/evidence graph.
- Reuse existing recurring-obligation records when new evidence refers to obligations MIRA already knows; never create duplicates merely because another source names them.
- Add genuinely missing recurring obligations through the same private recurring-finance path and canonical projection.
- Represent private allocations so derived free/discretionary cash excludes earmarked money exactly once.
- Update protected reserves only through established Financial Escape assumption paths.
- Expand spending-category vocabulary while preserving existing values.
- Carry purpose-category, necessity, allowance, optional vendor overrides, and optional review notes into the integrated `FinOps Ledger` by stable Event ID.
- Drive spending analytics from the integrated `FinOps Ledger` rather than directly from the input-control tab.
- Treat the spending-review tab as an input/view surface: effective category, effective vendor, month, and review status are read back from `FinOps Ledger`.
- Read back affected private formulas/values after writes and keep Android `M2-M1-012` recovery state exact.
