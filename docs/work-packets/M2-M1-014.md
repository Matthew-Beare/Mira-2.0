## Objective

Non-destructively reconcile newly shared household budget/income evidence into the existing MIRROR financial reality while preserving established history and forecast assumptions, then represent user-confirmed checking earmarks, protected project reserves, recurring allowance balances, recurring obligations, and practical spending-classification semantics without creating a second finance authority or double counting cash.

## Single-MIRROR invariant

MIRA has one logical MIRROR reality database. Financial Escape tabs are class tables, controls, source-evidence views, or derived projections inside that model; they are not independent databases or co-equal authorities.

- `Entity Registry` owns stable entity identity.
- `FinOps Relations` owns explicit provenance/evidence relationships.
- `FinOps Ledger` owns the integrated economic-event projection used by spending telemetry.
- `Subscriptions` owns the command-center recurring-obligation projection backed by provider/user evidence.
- `Planning Items` and the earmark/control view represent planned allocations without mutating provider balances.
- Source-budget and telemetry tabs are human-readable views over those facts. A materially different source view may preserve comparison values without becoming a second authority or overwriting the primary forecast.
- Human review tabs may collect explicit user inputs keyed by stable IDs, but resolved/effective state belongs to the canonical MIRROR class table and is read back into the view rather than recomputed as a competing truth.

## Scope / invariants

1. Newly shared budget/income sources are read-only evidence and comparison/scenario inputs, not permission to overwrite the existing Financial Escape budget basis.
2. Materially different source assumptions remain visible as a source-evidence view within the same MIRROR model; they do not become a separate database and do not destructively rewrite historical or forecast state.
3. Linked financial-provider balances remain provider observations; earmarks are allocation semantics only and must not alter provider balances.
4. Protected project reserves and checking earmarks remain distinct when their funding semantics differ, preventing double subtraction.
5. Existing transaction, daily-snapshot, normalized-spend, debt, mileage, and forecast history remains intact.
6. User-confirmed allowance balances are forward starting balances. Monthly accrual begins on the next applicable first-of-month boundary and does not retroactively add the current month.
7. The household allowance flow is one combined monthly allocation split between two individual balances; it must never be counted again as an additional household allowance obligation.
8. No purchase/debit automation against allowance balances is activated in this packet; future spend reconciliation remains separate work.
9. Spending classification keeps three independent axes: purpose category, necessity, and allowance. Vocabulary may expand without rewriting prior selections.
10. All private provider/document identifiers and private values remain outside public Git.

## Acceptance criteria

- Read shared budget/income sources without mutating them.
- Preserve the current Financial Escape core budget/forecast basis when replacing it would materially change existing outputs.
- Register source documents and their relationships in the same private entity/evidence graph.
- Reuse existing recurring/subscription records where shared-source lines refer to obligations MIRA already knows; never create duplicate bills merely because a second source names them.
- Add genuinely missing recurring obligations through the same private recurring-finance path and command-center subscription projection.
- Represent current checking earmarks and recurring allowance accruals so free/discretionary cash excludes earmarked money exactly once.
- Update protected project reserves only through established Financial Escape assumption paths.
- Expand the spending category vocabulary, including Entertainment and Vehicle Registration, while preserving existing values.
- Carry purpose-category, necessity, allowance, optional vendor overrides, and optional review notes into the integrated `FinOps Ledger` by stable Event ID.
- Drive telemetry from the integrated `FinOps Ledger` rather than directly from the input-control tab.
- Treat the spending-review tab as an input/view surface: effective category, effective vendor, month, and review status must be read back from `FinOps Ledger`, not independently recomputed there.
- Read back affected private formulas/values after writes and keep Android `M2-M1-012` recovery state exact.
