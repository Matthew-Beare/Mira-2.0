## Objective

Implement the provider-neutral deterministic safety-decision seam that later private sensor adapters and lifecycle executors can consume. Explicit configured sensor policies plus fresh observations must produce a reproducible normal/warning/critical/sensor-fault decision and bounded response requirements without an LLM inventing thresholds or directly controlling hardware.

The first slice is policy/evidence only. It must not read a real host sensor, call IPMI/NVML/Redfish, stop a process, drain a real scheduler, power off a machine, send Wake-on-LAN, modify worker registry state, or claim a live safe-shutdown path.

## Configuration contract

Each configured required sensor must declare:

- a generic sensor ID used only inside the private/runtime configuration boundary;
- an explicit unit token;
- whether higher or lower values are worse;
- an explicit warning threshold;
- an explicit critical threshold;
- a positive freshness window.

Threshold ordering is validated against direction:

- `high_is_bad`: warning must be strictly below critical;
- `low_is_bad`: warning must be strictly above critical.

No default CPU/GPU temperature, fan RPM, pump RPM, coolant temperature, power, voltage or other hardware threshold is supplied by public product code. Threshold values are configuration/evidence, not model guesses.

The node-level policy must explicitly configure whether a critical reading requests safe shutdown and whether a missing/stale required sensor requests safe shutdown. Those booleans must not be inferred from a machine name or hardware type.

## Observation contract

A sensor observation contains only sensor ID, numeric finite value, unit and UTC observed-at time. Evaluation receives an explicit UTC `now`.

- duplicate observations for one sensor fail closed;
- an observation for an unconfigured sensor is ignored rather than silently becoming safety authority;
- future observations are malformed and fail validation;
- required sensors with no observation are `sensor_fault`;
- required observations older than their configured freshness window are `sensor_fault`;
- unit mismatch is `sensor_fault` rather than comparing incompatible values.

## Severity semantics

Per-sensor severity is deterministic:

- `normal`: within configured safe side of warning;
- `warning`: warning threshold crossed but critical threshold not crossed;
- `critical`: critical threshold crossed;
- `sensor_fault`: required evidence is missing, stale, or unit-incompatible.

The node decision uses the most conservative aggregate class. `sensor_fault` and `critical` are both stop/fault classes; they remain distinguishable for provenance and operator diagnosis.

## Response requirements

This packet returns response requirements only. It executes nothing.

- `normal`: new work may be admitted; no drain/stop/fault/shutdown requirement.
- `warning`: do not admit new work and request drain; do not stop current workloads or fault the node solely from warning.
- `critical`: do not admit new work, request drain, require affected workloads to stop, and require node fault state. Safe shutdown is required only when explicitly enabled by node policy.
- `sensor_fault`: same conservative stop/fault behavior as critical because required safety evidence is unavailable. Safe shutdown is required only when explicitly enabled for sensor faults.

A later power/lifecycle packet owns execution, interactive/do-not-wake/do-not-shutdown lock reconciliation, provider-specific shutdown/WOL adapters and durable action readback. This packet cannot bypass those boundaries by itself.

## Evidence/provenance rules

The evaluation result must retain:

- policy ID;
- evaluated-at time;
- aggregate severity;
- deterministic reason codes;
- one bounded per-sensor result with configured direction/unit, evidence state, observed value/time when valid, and severity;
- the computed response requirements.

It must not contain hostnames, IPs, MACs, serial numbers, credentials, model paths, raw shell commands or private provider resource IDs.

## Acceptance evidence target

1. Policy validation rejects duplicate sensors, malformed IDs/units, non-finite thresholds, invalid threshold ordering and invalid freshness values.
2. Exact warning/critical boundary comparisons are tested for both high-is-bad and low-is-bad sensors.
3. Missing, stale, future and unit-mismatched evidence fail closed as specified.
4. Unknown extra observations do not acquire authority.
5. Aggregate severity is input-order independent and deterministic.
6. Warning blocks admission/requests drain without stopping workloads.
7. Critical and sensor-fault classes require stop + fault; shutdown follows explicit configuration only.
8. Returned public/synthetic evidence contains no private machine/network/credential material.
9. Production ownership is explicit with direct test verification.
10. Exact-head CI passes before merge and post-merge main CI passes before integration verification.
11. No live hardware-safety, shutdown, sensor or private deployment claim is made.
