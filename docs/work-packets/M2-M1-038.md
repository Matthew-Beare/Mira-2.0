## Objective

Implement the first stock-ChatGPT/no-app MIRA Studio intake boundary so a customer can describe a desired preference, workflow, or capability in ordinary language without supplying packet IDs, work IDs, change IDs, Git branches, providers, model names, or implementation details.

The deterministic boundary accepts the raw user request plus a host/model-produced semantic interpretation, validates that interpretation against the exact canonical feature registry, derives declared feature dependencies, generates stable private intake identity, preserves explicit customer constraints separately from assistant assumptions, surfaces materially unresolved blockers/questions, and emits one bounded reviewable draft plus one customer-facing next action.

The host/model may interpret natural language; this packet does not claim deterministic code can semantically understand arbitrary prose without such interpretation. The deterministic layer is the authority for validation, registry grounding, identity, constraint/assumption separation, dependency derivation, and whether a draft is ready for customer review.

This packet does not invoke a model, create Git branches, assign an implementation packet, mutate source/provider state, publish/share a feature, install an import, activate behavior, or implement final graphical Studio UX.

## Acceptance criteria

1. Customer-facing input requires only ordinary-language request plus any explicit constraints the customer actually stated.
2. Internal `draft_id` is deterministic and generated by MIRA; no customer-supplied packet/work/change/Git/provider identifiers are accepted as structured user input.
3. Semantic interpretation distinguishes preference/workflow/feature using `StudioChangeKind` and carries a concise desired outcome.
4. Proposed feature scope must be validated against the exact `FeatureRegistry`; unknown feature IDs fail closed.
5. Declared dependency scope is derived deterministically and transitively from the selected feature records rather than trusted from model prose.
6. Explicit customer constraints remain distinct from assistant/model assumptions.
7. Material unresolved questions/blockers keep the draft non-ready and yield exactly one customer-facing clarification action.
8. A fully grounded draft becomes review-ready but grants no implementation, source-mutation, publication, install, approval, or activation authority.
9. Identical normalized intake evidence + exact registry yields identical draft identity/projection; materially changed request/interpretation changes identity.
10. Intake rejects blank/oversized/control-character input, duplicate/unsorted internal evidence, unknown features, inconsistent echoed customer constraints, and attempts to smuggle execution authority.
11. Tests cover preference, workflow and feature intake, dependency derivation, ambiguity, assumptions, constraints, unknown scope, deterministic replay, authority escalation and malformed input.
12. Repository CI must pass on the exact packet head before merge; post-merge exact-SHA CI is required for integration verification.
