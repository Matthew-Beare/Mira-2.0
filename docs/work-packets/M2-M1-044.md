# M2-M1-044 — Deterministic reconciliation and pre-reply gate

## Objective

Implement one reusable deterministic run contract for recurring MIRA operations so the system must reconcile required evidence, validate mutations, checkpoint results and pass an explicit pre-reply gate before claiming state is current/updated/reconciled/done.

Customer-approved sweep:

`DISCOVER -> RECONCILE -> MUTATE -> REBUILD -> VERIFY -> CHECKPOINT -> REPLY`

This packet is the reusable orchestration/gating seam. It is not permission to implement every live provider adapter in one branch.

## Customer behavior to enable

For each recurring run, MIRA must:

1. resolve run identity/time/slot/context and declared required modules;
2. inspect each module's new evidence since its durable prior cursor/checkpoint;
3. reconcile duplicates/replays/matches/unresolved evidence;
4. perform only supported mutations through the module's canonical authority;
5. rebuild dependent projections after canonical state is reconciled;
6. verify required invariants and exact readback for mutations;
7. persist one durable run checkpoint with coverage/freshness/counts/blockers/cursors;
8. only then render a reply, preserving module failures explicitly instead of silently omitting them.

A reply may still be rendered when one independent module is blocked, but the gate must prevent unsupported success/currentness claims for that module and surface its exact blocker.

## Implemented deterministic contract

### Run identity

A run binds:

- `run_id`
- local date and IANA timezone
- slot/mode/context
- ordered module manifest
- previous durable cursors/markers supplied by modules

Duplicate module IDs, malformed identity, missing dependencies and dependency cycles fail before module execution.

### Module dispositions

Exactly one terminal disposition is required:

- `complete`
- `needs_review`
- `blocked`
- `not_applicable`

`needs_review` is not success; it is an explicit human-classification/reconciliation queue state. `blocked` carries a bounded blocker code. `not_applicable` is explicit rather than inferred from silence.

### Mutation/readback proof

For every module reporting canonical mutations:

- stable mutation IDs are required;
- every required mutation must have exact readback evidence represented by a verified SHA-256 readback fingerprint;
- duplicate mutation IDs fail;
- a module reporting `complete` with an unverified required mutation fails the run contract;
- modules that declare a required projection rebuild cannot remain complete unless that rebuild is verified;
- optional/non-authoritative evidence does not masquerade as canonical readback.

### Counts/freshness/checkpoint

Each module records bounded counts:

- discovered
- matched
- updated
- duplicate/replay
- unresolved

It also records source coverage/freshness and next durable cursor/marker when applicable. The run checkpoint stores normalized module results and a deterministic fingerprint.

### Durable persistence boundary

`ops/reconciliation_checkpoint_store.py` adapts the reconciliation checkpoint contract to MIRA's existing `StructuredStateAdapter`. It uses optimistic creation, idempotency, exact provider-neutral readback and checkpoint-fingerprint verification. A fresh sweep/store instance can recover the prior completed run and replay it without re-executing handlers. Corrupted/tampered checkpoint material fails closed.

The orchestration engine itself stays provider-neutral; provider/resource selection remains outside it.

### Pre-reply claim gate

The engine exposes whether the reply may use strong state claims. Claims such as `current`, `updated`, `reconciled`, `done`, `complete`, or `verified` are permitted for a module only when that module passed its required verification/readback contract. `current` additionally requires all applicable reported sources to have fresh/complete coverage. Blocked/review/unknown modules must be labelled accordingly.

### Replay and failure isolation

Once a completed checkpoint exists for the same deterministic `run_id` and manifest fingerprint, replay returns the checkpoint and does not execute module handlers again. Raw handler exceptions are collapsed to bounded blocker codes rather than persisted. Independent modules continue when another module fails, while dependent modules fail closed.
