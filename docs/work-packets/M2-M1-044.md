## Customer behavior to enable

For each recurring run, MIRA must:

1. resolve run identity/time/slot/context and declared required modules;
2. inspect each module's new evidence since its durable prior cursor/checkpoint;
3. reconcile duplicates/replays/matches/unresolved evidence;
4. perform only supported mutations through the module's canonical authority;
5. rebuild dependent projections after canonical state is reconciled;
6. verify required invariants and exact readback for mutations;
7. persist one durable run checkpoint with coverage/freshness/counts/blockers/cursors;
8. only then render a reply, preserving module failures explicitly instead of silently omitting them.

A reply may still be rendered when one independent module is blocked, but the gate must prevent unsupported success/currentness claims for that module and surface its exact blocker.

## Deterministic contract

### Run identity

A run binds:

- `run_id`
- local date and IANA timezone
- slot/mode/context
- ordered module manifest
- previous durable cursors/markers supplied by modules

Duplicate module IDs and malformed identity fail before module execution.

### Module dispositions

Exactly one terminal disposition is required:

- `complete`
- `needs_review`
- `blocked`
- `not_applicable`

`needs_review` is not success; it is an explicit human-classification/reconciliation queue state. `blocked` carries a bounded blocker code/message. `not_applicable` is explicit rather than inferred from silence.

### Mutation/readback proof

For every module reporting canonical mutations:

- stable mutation IDs are required;
- every required mutation must have exact readback evidence;
- duplicate mutation IDs fail;
- a module reporting `complete` with an unverified required mutation fails the run contract;
- optional/non-authoritative evidence does not masquerade as canonical readback.

### Counts/freshness/checkpoint

Each module records bounded counts:

- discovered
- matched
- updated
- duplicate/replay
- unresolved

It also records source coverage/freshness and next durable cursor/marker when applicable. The run checkpoint stores normalized module results and a deterministic fingerprint.

### Pre-reply claim gate

The engine exposes whether the reply may use strong state claims. Claims such as `current`, `updated`, `reconciled`, `done`, `complete`, or equivalent are permitted for a module only when that module passed its required verification/readback contract. Blocked/review/unknown modules must be labelled accordingly.

### Replay

Once a completed checkpoint exists for the same deterministic `run_id` and manifest fingerprint, replay returns the checkpoint and must not re-execute module handlers.

## Acceptance criteria

1. Deterministic run identity and manifest validation.
2. Ordered module execution with one terminal disposition each.
3. Exact readback required for all required canonical mutations before `complete`.
4. Explicit source coverage/freshness and reconciliation counts.
5. Independent blocked module isolation while preserving exact blockers.
6. Strong-claim pre-reply gate rejects unsupported state claims.
7. Durable checkpoint payload/fingerprint with module cursors/markers.
8. Completed-run replay is side-effect free.
9. Synthetic adversarial tests cover malformed manifests, duplicate IDs, thrown handlers, missing readback, review queue, blockers, successful multi-module run, replay and claim rejection.
10. No private data or provider identifiers enter public Git.
11. Exact-head CI green before merge; exact post-merge SHA/readback required before integration-verified closeout.
